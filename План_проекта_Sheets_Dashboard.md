# Веб-приложение на базе Google Sheets: технический план

## 1. Суть проекта

Веб-сервис, где **Google Sheets выступает единым источником данных** (сотрудники, проекты, оклады и т.д.), а сайт даёт:
- ролевой доступ (супер-админ / менеджер / оператор / наблюдатель);
- импорт Excel-файлов и автоматическую сверку с данными в Sheets;
- конструктор отчётов и дашбордов («выбрал галочками поля — получил сводную»);
- выгрузку итоговых данных обратно в Excel.

Бюджет — бесплатный старт, хостинг — облако, аудитория — 10+ пользователей с разными правами.

---

## 2. Структура данных в Google Sheets

Одна таблица (spreadsheet), несколько листов, связанных по ID — это правильный подход, его и оставляем.

| Лист | Ключевые поля | Комментарий |
|---|---|---|
| `Сотрудники` | `employee_id` (PK), ФИО, должность, оклад, дата приёма, статус (активен/уволен) | ID — текстовый уникальный код, не строка таблицы (строки могут смещаться) |
| `Проекты` | `project_id` (PK), название, площадь, стоимость проекта, дата начала/окончания, статус | Аналогично, свой ID |
| `Назначения / нагрузки` | `assignment_id`, `employee_id` (FK), `project_id` (FK), роль на проекте, ставка/загрузка, период | Это связующий лист — именно он превращает две плоские таблицы в реляционную модель |
| `Справочники` | должности, статусы, типы проектов | Чтобы в формах были выпадающие списки, а не свободный ввод |
| `Лог изменений` | дата, кто изменил, что изменил, старое/новое значение | Критично для аудита — вы поймёте, кто и когда скорректировал данные |

**Совет:** не храните ID как номер строки — если строку удалят или отсортируют, все связи "поедут". Генерируйте ID программно (например `EMP-0001`, `PRJ-0001`) при создании записи.

## 3. Логика сверки Excel ⇄ Sheets

Сценарий, который вы описали — классическая **сверка (reconciliation)**:

1. Оператор загружает Excel-файл на сайт.
2. Backend построчно сопоставляет записи по `employee_id` и `project_id` с данными в Sheets.
3. Результат разбивается на три группы:
   - **Совпало** — данные идентичны → сразу попадает в сводную.
   - **Есть в Excel, но отличается от Sheets** (например, другой оклад или загрузка) → помечается как расхождение.
   - **Есть в Excel, но отсутствует в Sheets** (новый сотрудник/проект) → помечается как "требует решения".
4. Расхождения не применяются автоматически — они уходят на экран **Менеджеру**, который либо подтверждает обновление Sheets, либо отклоняет.
5. После решений по всем расхождениям формируется финальная сводная — и это то, что видит Оператор и что можно выгрузить.

Это разумно разделить на статусы записи: `новое`, `расхождение`, `подтверждено`, `отклонено` — так на дашборде всегда видно, сколько записей "висит" в работе.

## 4. Матрица ролей

| Роль | Просмотр данных | Редактирование данных | Импорт Excel / сверка | Выдача ролей | Выгрузка отчётов |
|---|:---:|:---:|:---:|:---:|:---:|
| **Супер-админ** | ✓ всё | ✓ всё | ✓ | ✓ (по заявке через форму) | ✓ |
| **Менеджер** | ✓ всё | ✓ (в т.ч. подтверждает расхождения) | ✓ | — | ✓ |
| **Оператор** | ✓ (сводные, дашборды) | — | ✓ (загружает, но не правит основные данные) | — | ✓ (по своим отчётам) |
| **Наблюдатель** | ✓ всё | — | — | — | ✓ (только выгрузка) |

Механизм выдачи ролей, который вы описали (заявка через форму → супер-админ одобряет → доступ выставляется автоматически по указанной в форме позиции), — это готовый паттерн **"access request workflow"**. Реализуется как отдельная сущность "Заявки на доступ" со статусами `на рассмотрении / одобрено / отклонено`.

## 5. Конструктор отчётов ("лего")

Пример: "нужна сводная по нагрузкам" → пользователь галочками выбирает ФИО, проект, площадь, оклад, стоимость проекта → система строит сводную таблицу на лету.

Технически это:
- список доступных полей (с учётом того, из какого листа они берутся — Sheets гарантирует связь через `employee_id`/`project_id`);
- backend собирает SQL-подобный запрос (`SELECT выбранные_поля FROM объединённые_данные WHERE фильтры`);
- результат рендерится как таблица/дашборд на сайте и одновременно доступен для выгрузки в Excel.

Это единственное место в проекте, где **прямая работа с Google Sheets API становится узким местом**: Sheets не умеет быстро выполнять произвольные агрегации и имеет лимиты на количество запросов в минуту. Поэтому ниже в архитектуре предлагается промежуточный слой.

## 6. Рекомендуемый технический стек (бесплатный старт, облако, под Claude Code)

| Слой | Технология | Почему |
|---|---|---|
| Frontend | Next.js (React) | Один из самых быстрых способов получить сайт + API в одном проекте, отлично ложится на бесплатный тариф Vercel |
| Хостинг frontend/API | Vercel (free tier) | Бесплатно для старта, авто-деплой из Git, идеально сочетается с Next.js |
| Аутентификация и роли | Firebase Authentication + Firestore (custom claims для ролей) | Бесплатный тариф, готовая система логина, роли хранятся как custom claims у пользователя |
| "Быстрый" слой данных | Firestore (кэш-копия данных из Sheets) | Google Sheets API имеет лимиты (100 запросов/100 сек на пользователя) и не годится как БД для дашбордов в реальном времени. Firestore — это кэш, синхронизируемый с Sheets, а не замена Sheets |
| Источник истины | Google Sheets API (service account) | Как вы и задумали — люди привычны редактировать напрямую в Sheets, система читает/пишет туда же |
| Импорт/экспорт Excel | библиотека SheetJS (xlsx) | Разбор загруженных .xlsx на сервере и генерация выгрузок |
| Дашборды/графики | recharts или Chart.js | Готовые компоненты для визуализации на React |

**Важный архитектурный момент:** имеет смысл не работать с Google Sheets API напрямую на каждый клик пользователя (будет медленно и упрётесь в лимиты), а делать **одностороннюю или двустороннюю синхронизацию** между Sheets и Firestore:
- раз в N минут (или по кнопке "обновить") — подтягивать изменения из Sheets в Firestore;
- изменения, сделанные на сайте (например, менеджер подтвердил расхождение) — записывать обратно в Sheets через API.

Это решает проблему скорости дашбордов и сохраняет Google Sheets как понятный людям источник данных.

## 7. Дорожная карта (MVP по этапам)

1. **Подготовка** — создать Google Cloud проект, включить Sheets API, создать service account, спроектировать финальную структуру листов.
2. **Аутентификация и роли** — Firebase Auth, форма заявки на доступ, панель супер-админа для одобрения.
3. **Синхронизация с Sheets** — чтение данных в Firestore, отображение в виде таблиц на сайте.
4. **Импорт Excel и сверка** — загрузка файла, сопоставление по ID, экран расхождений для менеджера.
5. **Конструктор отчётов и дашборды** — выбор полей, фильтры, визуализация.
6. **Экспорт в Excel** — выгрузка сводных таблиц.
7. **Лог изменений и тестирование** — аудит действий, проверка ролей, деплой на Vercel.

Каждый этап — это законченный кусок, который можно показать и проверить, не дожидаясь всего проекта целиком.

## 8. Что стоит решить до начала разработки

- Финальный список полей на каждом листе Sheets (см. раздел 2) — лучше зафиксировать сразу, переделывать структуру данных на середине проекта дорого.
- Точный список полей для конструктора отчётов (раздел 5) — хотя бы 2-3 примера готовых отчётов, которые нужны "прямо сейчас".
- Кто у вас будет супер-админом на старте и какие позиции/должности существуют в компании — от этого зависит форма заявки на доступ.
